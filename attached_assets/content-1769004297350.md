# Working with Authentication

_Authentication_ is the process by which your application gains the ability to access Vimeo data and resources through the API. There are several ways that you can go about this, depending on the type of data that your app needs to access and the particular conditions under which you're accessing it. You'll learn about them all in this tutorial.

**NOTE:** This information is current for our latest API release, version 3.4. For complete details on 3.4, see our [Changelog](https://developer.vimeo.com/api/changelog).

## Before you begin

To use this guide, you need:

- **A registered API app.** This is what's interacting with the API and requesting authentication. Haven't registered yet? See [Getting Started: The Basics](https://developer.vimeo.com/api/guides/start).

**NOTE:** You might also consider using our official libraries for PHP, Python, Node.js, and a dozen other programming languages. The libraries help to simplify complicated coding by handling all the HTTP requests on your behalf. For more information, see our [Libraries and SDKs](https://developer.vimeo.com/api/libraries) page.

## Understanding the authentication process

The Vimeo API uses the open [OAuth 2.0](https://oauth.net/) standard for all your app-authentication needs. Under the OAuth 2.0 framework, a third party — that's you — asks a resource owner — that's your app's end user — for permission to access their Vimeo data. If the resource owner grants this permission, we issue you an _access token_. This is a special string of characters that works like a password. You present the access token with your API requests whenever you're asking for protected information.

What we've just described is an _authenticated_ access token, because it's tied to a particular Vimeo member's private data. But not all Vimeo data is private. Some of it is publicly available, so that a third party — you again — doesn't need anyone's permission to access it. You still need to obtain an access token, though, because we need to know who's asking for this data. An _unauthenticated_ access token serves this purpose. It isn't tied to a particular Vimeo member, but it does get you into the lobby, so to speak, for access to our public data. You can access public data with an authenticated access token, too; it's not exclusively for private data. It's also the type of token that you need to perform certain actions like uploading videos. But an unauthenticated access token is always for public data only.

**NOTE:** If your app accesses the private data of multiple Vimeo members, you need a separate authenticated access token specific to each account.

An access token has one or more scopes, or general domains. The scopes determine the types of access that token does and doesn't permit. During the authentication process, you can specify exactly which scopes your app needs based on the list in [Table 1](https://developer.vimeo.com/api/authentication#table-1). If you try to make an API request with an access token that doesn't have the right scope, the API will deny the request.

_Table 1. Access scopes_

| Scope | Enables your app to |
| --- | --- |
| `public*` | Access public member data. |
| `private†` | Access private member data. |
| `purchased` | Access a member's Vimeo On Demand purchase history. |
| `create` | Create new Vimeo resources like showcases, groups, channels, and portfolios. To create new videos, you need the `upload` scope. |
| `edit` | Edit existing Vimeo resources, including videos. |
| `delete` | Delete existing Vimeo resources, including videos. |
| `interact` | Interact with Vimeo resources, such as liking a video or following a member. |
| `stats` | Be able to access video stats. Please note that this scope doesn't automatically grant your app the necessary capabilities for specific stats. |
| `upload` | Upload videos. |
| `promo_codes` | Add, remove, and review Vimeo On Demand promotions. |
| `video_files` | Access video files belonging to members with Vimeo Standard membership or higher. |

\\* An authenticated access token with the `public` scope is identical to an unauthenticated access token, except that you can use the `/me` endpoint to refer to the currently logged-in user. Accessing `/me` with an unauthenticated access token generates an error.

† Required for any scope other than `public`.

**NOTE:** Expiration times for access tokens vary, depending on the type of the token and the way that the token is granted. Some access tokens have a limited lifespan. Others continue to work indefinitely, as long as you use them on a regular basis. To keep things running smoothly on our end, we automatically delete any tokens that appear to be inactive. For more information, see the descriptions of the individual authentication workflows below.

## Understanding authentication workflows

OAuth 2.0 supports a number of different methods or _workflows_ for authentication based on the _grant type_, or the way in which authentication is granted.

For the purposes of the Vimeo API, there are four grant types: client credentials, authorization code, implicit, and device code. You want to choose the one that works the best for your particular circumstances.

We'll have more to say about each grant type when we go through the workflows step by step. In the meantime, [Table 2](https://developer.vimeo.com/api/authentication#table-2) provides a quick summary.

_Table 2. Summary of grant types_

| Grant type | Enables access to | Use when |
| --- | --- | --- |
| Client credentials | Public data | You don't need access to private data. |
| Authorization code | Public data, private data | You need long-term access. |
| Implicit | Public data, private data | You can't properly secure your app's client secret from your end users. |
| Device code | Public data, private data | Your app runs on a browserless or limited-input device. |

**NOTE:** We also support the basic authentication workflow, which doesn't have anything to do with OAuth or grant types. We don't recommend this kind of authentication in most cases, because using it can lead to security problems. With that proviso, see [Working with basic authentication](https://developer.vimeo.com/api/authentication#working-with-basic-authentication) below for more information.

## Obtaining an access token

So to summarize what we've covered so far: if you want to make API requests, you need to have an access token. And if you want to get an access token, you need to follow an authentication workflow. But which of the workflows is best for you? And what are the steps? And how do they work?

The following sections explain the grant types in detail and take you through the workflows from start to finish.

**NOTE:** Are you in the market for a personal access token? Do you want to generate it here on the developer site instead of through the API? See [Getting Started: The Basics](https://developer.vimeo.com/api/guides/start#generate-access-token) for step-by-step instructions.

### Using the client credentials grant

The _client credentials_ grant provides access to public data only. You don't need permission from your end user for that, so the entire authentication workflow happens without their participation.

Here are the general steps:

- [**Step 1.** Make a POST request.](https://developer.vimeo.com/api/authentication#using-the-client-credentials-grant-step-1)
- [**Step 2.** Get the access token.](https://developer.vimeo.com/api/authentication#using-the-client-credentials-grant-step-2)

### [1](https://developer.vimeo.com/api/authentication\#using-the-client-credentials-grant-step-1)

Make a POST request to `/oauth/authorize/client`:

```
POSThttps://api.vimeo.com/oauth/authorize/client
```

[Table 3](https://developer.vimeo.com/api/authentication#table-3) shows the headers to send. For the `Authorization` header, you need your app's client identifier and client secret, both of which appear on the app's information page. To access this page, go to [My Apps](https://developer.vimeo.com/apps).

_Table 3. Headers for POST to `/oauth/authorize/client` in the client credentials grant_

| Header | Set value to |
| --- | --- |
| `Authorization` | `basic base64_encode(x:y),` where `x` is the client identifier and `y` is the client secret |
| `Content-Type` | `application/json` |
| `Accept` | `application/vnd.vimeo.*+json;version=3.4` |

**NOTE:** Don't omit the `Accept` header in this request (and all subsequent requests in this guide), and always be sure to set it to the given value. This ensures that the API handles your response according to version 3.4. For more information, see [Using Common Formats and Parameters](https://developer.vimeo.com/api/common-formats#using-the-accept-header).

In the body of the request, set the `grant_type` field to `client_credentials`; this is required.

```
{
  "grant_type": "client_credentials",
  "scope": "public"
}
```

**NOTE:** You can't use the access token from the client credentials grant to get anything other than public data, even if you specify additional scopes.

[Table 4](https://developer.vimeo.com/api/authentication#table-4) presents descriptions of common errors for this API request.

_Table 4. Common errors for POST to `/oauth/authorize/client` in the client credentials grant_

| HTTP code | Error code | Description |
| --- | --- | --- |
| 400 | 2204 | You have an invalid value for the grant\_type field. |
| 401 | 8001 | We don't recognize your API app. |

### [2](https://developer.vimeo.com/api/authentication\#using-the-client-credentials-grant-step-2)

The response from the API includes the access token string among some other technical details (see [Table 5](https://developer.vimeo.com/api/authentication#table-5)).

```
{
  "access_token": "{token}",
  "token_type": "bearer",
  "scope": "{scope_list}"
}
```

_Table 5. OAuth response fields in the client credentials grant_

| Field | Description |
| --- | --- |
| `access_token` | The access token string. |
| `token_type` | The type of the access token. For the Vimeo API, the value of this field is always `bearer`. |
| `scope` | The space-separated list of scopes associated with the access token. The default value is `public`. Any other scopes that you may have specified in [Step 1](https://developer.vimeo.com/api/authentication#using-the-client-credentials-grant-step-1) are ignored. |

### Using the authorization code grant

With the _authorization code_ grant, the end user explicitly consents for your app to access their private data, including exactly which scopes to permit or deny. The front end and logic of the consent mechanism are all on our side; you send your end user to us through a browser, and we take care of it. You don't even need to log them in. We send them back to you with an authorization code, which you present to the API in exchange for an access token. Unlike in the [implicit grant](https://developer.vimeo.com/api/authentication#using-the-implicit-grant), this access token resides on the server, and it remains active as long as we perceive that you're using it.

Here are the general steps:

- [**Step 1.** Send your end user to the authorization URL.](https://developer.vimeo.com/api/authentication#using-the-auth-code-grant-step-1)
- [**Step 2.** Receive access permission from your end user.](https://developer.vimeo.com/api/authentication#using-the-auth-code-grant-step-2)
- [**Step 3.** Get the authorization code.](https://developer.vimeo.com/api/authentication#using-the-auth-code-grant-step-3)
- [**Step 4.** Send us the authorization code.](https://developer.vimeo.com/api/authentication#using-the-auth-code-grant-step-4)
- [**Step 5.** Get the access token.](https://developer.vimeo.com/api/authentication#using-the-auth-code-grant-step-5)

### [1](https://developer.vimeo.com/api/authentication\#using-the-auth-code-grant-step-1)

Direct your end user to the following address:

```
https://api.vimeo.com/oauth/authorize?response_type=code&client_id={client_id}&redirect_uri={redirect_uri}&state={state}&scope={scope_list}
```

See [Table 6](https://developer.vimeo.com/api/authentication#table-6) for details about the query parameters.

_Table 6. Query parameters for `/oauth/authorize` in the authorization code grant_

| Query parameter | Description |
| --- | --- |
| `response_type` | The OAuth response type. Use `code` for the authorization code grant. |
| `client_id` | The client identifier of your app. To get this value, access your app's information page from [My Apps](https://developer.vimeo.com/apps). |
| `redirect_uri` | A redirect URI associated with your app. To add or review redirect URIs, access your app's information page from [My Apps](https://developer.vimeo.com/apps). |
| `state` | An arbitrary value. We return this value to you later as a security measure. |
| `scope` | The space-separated list of scopes that you want to be able to access. This field is optional, and its default value is `public private`. |

It doesn't matter how you get your end user to the authorization URL. One of the most common ways is to include the link on a web page. Just make sure that you use the correct parameter values for `response_type`, `redirect_uri`, `scope`, and so on. If you don't, the request fails, and the standard Vimeo 404 page loads.

### [2](https://developer.vimeo.com/api/authentication\#using-the-auth-code-grant-step-2)

As soon as your end user arrives, we enable them to create a new Vimeo account if they don't already have one or log into their existing Vimeo account (assuming that they aren't already logged in), and then we ask them to accept or deny your app's request to access their private information. They can also choose which access scopes to permit if you asked for any scope other than `public`.

### [3](https://developer.vimeo.com/api/authentication\#using-the-auth-code-grant-step-3)

Once they accept, we send them to the redirect URI, along with the code and state query parameters:

```
{redirect_uri}?code={code}&state={state}
```

See [Table 7](https://developer.vimeo.com/api/authentication#table-7) for more information.

_Table 7. Query parameters appended to the redirect URI in the authorization code grant_

| Query parameter | Description |
| --- | --- |
| `code` | The authorization code to exchange for an access token. |
| `state` | The value that you specified for the `state` query parameter in the authorization URL. If this value doesn't match the original, don't attempt to exchange the code for a token. |

**NOTE:** We retain any custom query parameters that you include with your URI.

### [4](https://developer.vimeo.com/api/authentication\#using-the-auth-code-grant-step-4)

You now have the authorization code that you can exchange for an access token, so make a POST request to `/oauth/access_token`:

```
POSThttps://api.vimeo.com/oauth/access_token
```

The headers to send appear in [Table 8](https://developer.vimeo.com/api/authentication#table-8). You can get your app's client identifier and client secret, which you need for the `Authorization` header, from the app's information page at [My Apps](https://developer.vimeo.com/apps).

_Table 8. Headers for POST to `/oauth/access_token` in the authorization code grant_

| Header | Set value to |
| --- | --- |
| `Authorization` | `basic base64_encode(x:y),` where `x` is the client identifier and `y` is the client secret |
| `Content-Type` | `application/json` |
| `Accept` | `application/vnd.vimeo.*+json;version=3.4` |

In the request body, send the `grant_type` field with the value `authorization_code`. You must also set `code` to the authorization code string that you just received and `redirect_uri` to the redirect URI that you specified previously — don't use a different redirect URI.

```
{
  "grant_type": "authorization_code",
  "code": "{code}",
  "redirect_uri": "{redirect_uri}"
}
```

See [Table 9](https://developer.vimeo.com/api/authentication#table-9) for descriptions of common errors.

_Table 9. Common errors for POST to `/oauth/access_token` in the authorization code grant_

| HTTP code | Error code | Description |
| --- | --- | --- |
| 400 | `invalid_token` | Your code isn't valid, or the callback and the redirect URI don't match. |
| 400 | `unsupported_grant_type` | The value of the `grant_type` field isn't `authorization_code`. |

### [5](https://developer.vimeo.com/api/authentication\#using-the-auth-code-grant-step-5)

The API responds with the access token and details about the authenticated user (see [Table 10](https://developer.vimeo.com/api/authentication#table-10)).

```
{
  "access_token": "{token}",
  "token_type": "bearer",
  "scope": "{scope_list}",
  "user": "{user_representation}"
}
```

_Table 10. OAuth response fields in the authorization code grant_

| Field | Description |
| --- | --- |
| `access_token` | The access token string. |
| `token_type` | The type of the access token. For the Vimeo API, the value of this field is always `bearer`. |
| `scope` | The space-separated list of scopes that your app has permission to access. |
| `user` | The complete representation of the authenticated end user. For more information, see the [API Reference](https://developer.vimeo.com/api/reference/users#get_user). |

### Using the implicit grant

With the _implicit grant_, your app gains access to private data, but the workflow is abbreviated. You don't receive an authorization code to exchange for an access token like you do in the [authorization code grant](https://developer.vimeo.com/api/authentication#using-the-auth-code-grant). The API just gives you the access token, and you get it through the browser, as part of a URL. The access token has a one-hour lifespan.

To obtain an access token with the implicit grant, first make sure that your app is set up for it. Go to [My Apps](https://developer.vimeo.com/apps), open your app's information page, look under the settings for OAuth redirect authentication, and, if necessary, click the control for enabling implicit authentication.

Once you're sure that you've turned on this setting, here are the general steps:

- [**Step 1.** Send your end user to the authorization URL.](https://developer.vimeo.com/api/authentication#using-the-implicit-grant-step-1)
- [**Step 2.** Receive access permission from your end user.](https://developer.vimeo.com/api/authentication#using-the-implicit-grant-step-2)
- [**Step 3.** Get the access token.](https://developer.vimeo.com/api/authentication#using-the-implicit-grant-step-3)

### [1](https://developer.vimeo.com/api/authentication\#using-the-implicit-grant-step-1)

Send your end user here:

```
https://api.vimeo.com/oauth/authorize?response_type=token&client_id={client_id}&redirect_uri={redirect_uri}&state={state}&scope={scope_list}
```

For descriptions of the query parameters, see [Table 11](https://developer.vimeo.com/api/authentication#table-11).

_Table 11. Query parameters for `/oauth/authorize` in the implicit grant_

| Query parameter | Description |
| --- | --- |
| `response_type` | The OAuth response type. Use `token` for the implicit grant. |
| `client_id` | The client identifier of your app. To get this value, access your app's information page from [My Apps](https://developer.vimeo.com/apps). |
| `redirect_uri` | A redirect URI associated with your app. To add or review redirect URIs, access your app's information page from [My Apps](https://developer.vimeo.com/apps). |
| `state` | An arbitrary value. The API returns this value to you later as a security measure. |
| `scope` | The space-separated list of scopes that you want to be able to access. This field is optional, and its default value is `public private`. |

If the values of these parameters are invalid, the request fails, and your end user goes to the Vimeo 404 page.

### [2](https://developer.vimeo.com/api/authentication\#using-the-implicit-grant-step-2)

What happens next is similar to [Step 2 of the authorization code grant](https://developer.vimeo.com/api/authentication#using-the-auth-code-grant-step-2). Your end user creates a new account or logs in, accepts or denies your app's request for access, and chooses which scopes (other than `public`) to allow.

### [3](https://developer.vimeo.com/api/authentication\#using-the-implicit-grant-step-3)

We send the end user to your redirect URI, but we append the access token to it, along with other information, in a URL fragment (the part after the hash sign):

```
{redirect_uri}#access_token={access_token}&token_type=bearer&scope={scope_list}&state={state}&expires_in={expires_in}
```

See [Table 12](https://developer.vimeo.com/api/authentication#table-12) for descriptions of these fields.

_Table 12. Fields appended to the redirect URI in the implicit grant_

| Field | Data type | Description |
| --- | --- | --- |
| `access_token` | String | The access token string. |
| `token_type` | String | The type of the access token, which for the Vimeo API is always `bearer`. |
| `scope` | String | The plus-separated list of scopes that your app has permission to access. |
| `state` | String | The value that you specified for the `state` query parameter in the authorization URL. Be sure that this value matches the original. If it doesn't, a third party might be attempting to hijack the authorization process. |
| `expires_in` | Integer | The lifespan of the access token, in seconds. After this amount of time passes, the token automatically expires. |

If your redirect URI includes query parameters, we return them, but we strip out any custom URL fragment, again as marked by the hash sign. So if you give us the following as the redirect URI:

```
https://www.example.com?queryparam=queryvalue#customparam=customvalue
```

We remove everything after the hash sign and substitute the fields from [Table 12](https://developer.vimeo.com/api/authentication#table-12) above.

```
https://www.example.com?queryparam=queryvalue#access_token={access_token}&token_type=bearer&scope={scope_list}&state={state}&expires_in={expires_in}
```

### Using the device code grant

Not every internet-connected device includes a browser, and many of these devices are _input-constrained_, or difficult to use to enter information. The _device code grant_ is for cases like these. In this workflow, the browserless device displays a special URL and code. Your end user switches to a computer or tablet, opens a browser, goes to the URL, and enters the code. Back in the browserless device, your app intercepts that the code has been entered and receives an access token from the API.

Here are the general steps:

- [**Step 1.** Make a POST request.](https://developer.vimeo.com/api/authentication#using-the-device-code-grant-step-1)
- [**Step 2.** Get the user code, authorization endpoint, and activation link.](https://developer.vimeo.com/api/authentication#using-the-device-code-grant-step-2)
- [**Step 3.** Send your end user to the activation link to enter the user code.](https://developer.vimeo.com/api/authentication#using-the-device-code-grant-step-3)
- [**Step 4.** Poll the authorization endpoint.](https://developer.vimeo.com/api/authentication#using-the-device-code-grant-step-4)
- [**Step 5.** Get the access token.](https://developer.vimeo.com/api/authentication#using-the-device-code-grant-step-5)

### [1](https://developer.vimeo.com/api/authentication\#using-the-device-code-grant-step-1)

Make a POST request to `/oauth/device`:

```
POSThttps://api.vimeo.com/oauth/device
```

Along with this request, be sure to send some headers (see [Table 13](https://developer.vimeo.com/api/authentication#table-13)). The client identifier and client secret that you need to complete the value of `Authorization` are on your app's information page, which you can open from [My Apps](https://developer.vimeo.com/apps).

_Table 13. Headers for POST to `/oauth/device` in the device code grant_

| Header | Set value to |
| --- | --- |
| `Authorization` | `basic base64_encode(x:y),` where `x` is the client identifier and `y` is the client secret |
| `Content-Type` | `application/json` |
| `Accept` | `application/vnd.vimeo.*+json;version=3.4` |

Use the body of the request to send the `grant_type` field. Set this value to `device_grant`. If you want to request specific scopes, include a space-separated list in the `scope` field. If you don't make a specific request, the default `scope` value is `public private`.

```
{
  "grant_type": "device_grant",
  "scope": "{scope_list}"
}
```

Did something go wrong? See [Table 14](https://developer.vimeo.com/api/authentication#table-14) for common errors.

_Table 14. Common errors for POST to `/oauth/device` in the device code grant_

| HTTP code | Error code | Description |
| --- | --- | --- |
| 400 | 2204 | You have an invalid value for the `grant_type` field. |
| 401 | 8001 | We don't recognize your API app. |

### [2](https://developer.vimeo.com/api/authentication\#using-the-device-code-grant-step-2)

The API comes back with a number of fields, which we summarize in [Table 15](https://developer.vimeo.com/api/authentication#table-15), but pay particular attention to `user_code`, `authorize_link`, and `activate_link`. You'll need these values to proceed.

_Table 15. First set of OAuth response fields in the device code grant_

| Field | Description |
| --- | --- |
| `device_code` | A unique identifier for the end user's device. |
| `user_code` | The code that the end user must enter. |
| `authorize_link` | The authorization endpoint: `https://api.vimeo.com/oauth/device/authorize` |
| `activate_link` | The URL that the end user must visit to enter the value of `user_code`. |
| `expires_in` | The lifespan of the user code, in seconds. After 3600 seconds, the user code expires. |
| `interval` | The number of seconds that you should wait between checks when polling the authorization endpoint. |

### [3](https://developer.vimeo.com/api/authentication\#using-the-device-code-grant-step-3)

Instruct the end user to find a browser, visit the URL in `activate_link`, and enter the code in `user_code`. Be sure to take the following design considerations into account:

- Display the value of `user_code` in an area wide enough to hold a sequence of eight `8` characters, `88888888`, without clipping.
- The value of `activate_link` has no preset upper limit in terms of its length, although we try to keep it to as few characters as possible.
- Don't alter the values of `activate_link` or `user_code` in any way. The end user must visit that precise URL and enter that precise code.

When the end user arrives at the activation URL in their browser, they get a Vimeo-branded form for entering their user code. Assuming that they enter the code correctly, we prompt them to log into their Vimeo account, and then we ask them if it's okay for your app to access their private data. They can also choose exactly which scopes to permit or deny.

### [4](https://developer.vimeo.com/api/authentication\#using-the-device-code-grant-step-4)

You can start polling the `authorize_link` URL for the end user's response as soon as you get the initial set of OAuth fields from the API (but don't poll more quickly than the value in `interval`). Use a POST request for this:

```
POST{authorize_link}
```

See [Table 16](https://developer.vimeo.com/api/authentication#table-16) for the appropriate headers. To get the client identifier and client secret for the `Authorization` header, go to [My Apps](https://developer.vimeo.com/apps), and open your app's information page.

_Table 16. Headers for POST to the authorization link in the device code grant_

| Header | Set value to |
| --- | --- |
| `Authorization` | `basic base64_encode(x:y),` where `x` is the client identifier and `y` is the client secret |
| `Content-Type` | `application/json` |
| `Accept` | `application/vnd.vimeo.*+json;version=3.4` |

In the body of the request, set the `user_code` field to the user code and the `device_code` field to the device code. Both fields are required.

```
{
  "user_code": "{user_code}",
  "device_code": "{device_code}"
}
```

If you run into errors, see [Table 17](https://developer.vimeo.com/api/authentication#table-17).

_Table 17. Common errors for POST to the authorization link in the device code grant_

| HTTP code | Error code | Description |
| --- | --- | --- |
| 400 | `invalid_token` | The code is invalid, the code has expired, or the code doesn't match the device. |
| 400 | `user_rejected_connection` | The end user has declined your app's request to access their personal data. |

### [5](https://developer.vimeo.com/api/authentication\#using-the-device-code-grant-step-5)

In the response from the API, assuming that the end user has entered the code, you get the access token and the end user's details (see [Table 18](https://developer.vimeo.com/api/authentication#table-18)).

```
{
  "access_token": "{token}",
  "token_type": "bearer",
  "scope": "{scope_list}",
  "user": "{user_representation}"
}
```

_Table 18. Second set of OAuth response fields in the device code grant_

| Field | Description |
| --- | --- |
| `access_token` | The access token string. |
| `token_type` | The type of the access token. For the Vimeo API, the value of this field is always bearer. |
| `scope` | The space-separated list of scopes that your app has permission to access. |
| `user` | The complete representation of the authenticated end user. For more information, see the [API Reference](https://developer.vimeo.com/api/reference/users#get_user). |

## Presenting the access token to the API

Whenever an API request requires an access token, include the `Authorization` header with the request, and set the value of this header to `bearer {token}`, where the placeholder represents the access token string. Here's an example of what it looks like in cURL:

```
curl -H "Authorization: bearer {token}" https://api.vimeo.com
```

If you forget the `bearer` keyword, or if the API doesn't recognize the access token string, or if you've omitted the `Authorization` header entirely, we return HTTP status 401 Authorization Required along with error code 8003.

If you're unable to provide your token through the `Authorization` header, you might be able to send it by the `access_token` query parameter instead, like this (again in cURL):

```
curl https://api.vimeo.com/?access_token={token}
```

But doing it this way could leak the token string to browsers, proxies, and multiple services. Because of this potential security vulnerability, the only access tokens that work as query parameters are those with the `public` scope.

## Working with basic authentication

In addition to OAuth 2.0, the Vimeo API also supports basic authentication. It's easier to implement than the workflows that we've already discussed, but it's also potentially less secure, so we don't recommend it for general use. And it restricts the kinds of information that you can fetch from the API: metadata is out, for example. However, in some limited cases, when acquiring an access token is awkward or unfeasible, and it's sufficient for you to view the API from the perspective of a logged-out user, basic authentication might provide a way forward.

**NOTE:** Basic authentication doesn't identify the end user of an app, but it does identify the app itself.

To use basic authentication:

1. Get the client identifier and client secret of the app that's interacting with the API. You can find this information on your app's information page, which you can access from [My Apps](https://developer.vimeo.com/apps).
2. Create a string from the client identifier, a colon (`:`), and the client secret, like this:


```
{client_id}:{client_secret}
```

3. Base64-encode this string.
4. Take the `Authorization` HTTP header, and set its value as `basic` plus the encoded credentials from Step 3, like this:


```
Authorization: basic {encoded_credentials}
```

5. Include this header with your request.
